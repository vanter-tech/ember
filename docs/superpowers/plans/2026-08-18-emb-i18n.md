# EMB-i18N Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove hardcoded UI strings from the Ember tenant frontend and ship a Spanish/English language switcher next to the "Ember" wordmark, so any user can change the app's language on demand.

**Architecture:** A Zustand `persist` store (`localeStore`) holds the active locale in `localStorage`. Typed dictionary files under `locales/{es,en}/*.ts`, one per role namespace, are looked up through a `useTranslation(namespace)` hook. Each `en/*.ts` file is declared `satisfies typeof` its `es/*.ts` counterpart so `tsc -b` fails the build on any missing/extra translation key. A shared `LanguageSwitcher` component (built on the existing Radix `ui/select.tsx`) is dropped next to the wordmark in the 4 places it appears in the tenant app.

**Tech Stack:** React 19, TypeScript, Zustand 5 (`persist` middleware, already used by `authStore`/`sessionStore`), Radix `Select` (already a dependency via `components/ui/select.tsx`), Vitest + Testing Library (existing `Button.smoke.test.tsx` pattern).

**Spec:** `docs/superpowers/specs/2026-08-18-emb-i18n-design.md`

## Global Constraints

- **No backend changes.** Locale lives only in `localStorage` via `localeStore`. Never touch `User`, `RestaurantSettings`, or any backend module.
- **`/console` (Platform Operator portal) is out of scope.** Never touch `pages/console/**` or `layouts/PlatformLayout.tsx`.
- **No react-i18next / no new dependencies.** Only the custom store + dictionaries described below.
- **No browser-language auto-detection.** Default locale is always `'es'`.
- **Preserve existing text exactly in whichever locale it currently displays in — do not "fix" typos or missing accents while extracting.** E.g. `Categorias` (missing accent) and `Codigo de la mesa` (missing accent) must be copied verbatim into their locale's dictionary; do not silently correct them. This is a string-extraction task, not a copy-editing pass.
- **Key naming:** flat `camelCase` keys within a namespace object (no nested objects, no dot paths).
- **Interpolation syntax:** `{{varName}}` inside a dictionary string, consumed via `t('key', { varName: value })`.
- **Every dictionary source file (`es/*.ts` and `en/*.ts`) must NOT use `as const`.** Property types must stay widened to `string` (the default for a plain object literal) so `satisfies typeof esX` in the `en/*.ts` file checks key parity only, not exact string content — an `as const` on the ES side would make TypeScript require the EN strings to be character-for-character identical to the ES strings, which is wrong.
- **Zod validation messages and `react-hot-toast` copy are explicitly deferred to Task 8 (EMB-i18N-08).** Tasks 2–7 touch only JSX-rendered text (headings, labels, placeholders, `title`/`aria-label` attributes) — never a `z.object(...)` schema or a `toast.success/error(...)` call. This is intentional per the spec, not an oversight.
- **Per-task verification (every task, no exceptions):** `cd frontend && pnpm run build` must pass (this is the primary safety net — it catches missing/extra dictionary keys via the `satisfies` check, per CLAUDE.md's zero-tolerance TS-error policy), plus a manual pass toggling `LanguageSwitcher` on the pages that task touched.
- **This codebase has exactly one existing frontend test** (`src/test/Button.smoke.test.tsx`, a plain Vitest + Testing Library smoke test, no unit tests per page). Tasks 2–8 are mechanical string-extraction with no new branching logic, so they follow the project's own established convention of build-verification instead of inventing new per-page unit tests. Only Task 1 (real new logic: store + hook + component) gets a smoke test.

- [ ] **Step 5: Create the translation hook**

`frontend/src/lib/i18n.ts`:
```ts
import { useLocaleStore } from '@/store/localeStore'
import { dictionaries, type Namespace } from '@/locales'
import type { Locale, TranslationVars } from '@/locales/types'

const interpolate = (template: string, vars?: TranslationVars): string => {
  if (!vars) return template
  return Object.entries(vars).reduce(
    (result, [key, value]) => result.replaceAll(`{{${key}}}`, String(value)),
    template
  )
}

export const useTranslation = <N extends Namespace>(namespace: N) => {
  const rawLocale = useLocaleStore((state) => state.locale)
  const setLocale = useLocaleStore((state) => state.setLocale)
  // Defends against a corrupted/unrecognized value in localStorage — anything
  // that isn't exactly 'en' collapses to the 'es' default rather than crashing.
  const locale: Locale = rawLocale === 'en' ? 'en' : 'es'

  const t = (
    key: keyof (typeof dictionaries)['es'][N],
    vars?: TranslationVars
  ): string => {
    const dict = dictionaries[locale][namespace] as Record<string, string>
    const value = dict[key as string]
    if (value === undefined) {
      if (import.meta.env.DEV) {
        console.warn(
          `[i18n] missing key "${String(key)}" in namespace "${namespace}" (${locale})`
        )
      }
      const esDict = dictionaries.es[namespace] as Record<string, string>
      return esDict[key as string] ?? String(key)
    }
    return interpolate(value, vars)
  }

  return { t, locale, setLocale }
}
```

- [ ] **Step 6: Create the LanguageSwitcher component**

`frontend/src/components/LanguageSwitcher.tsx`:
```tsx
import { useTranslation } from '@/lib/i18n'
import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from '@/components/ui/select'
import type { Locale } from '@/locales/types'

export const LanguageSwitcher = () => {
  const { t, locale, setLocale } = useTranslation('common')

  return (
    <Select value={locale} onValueChange={(value) => setLocale(value as Locale)}>
      <SelectTrigger
        data-testid="language-switcher-trigger"
        aria-label={t('languageSwitcherLabel')}
        size="sm"
      >
        <SelectValue>{locale.toUpperCase()}</SelectValue>
      </SelectTrigger>
      <SelectContent>
        <SelectItem value="es">{t('languageSpanish')}</SelectItem>
        <SelectItem value="en">{t('languageEnglish')}</SelectItem>
      </SelectContent>
    </Select>
  )
}
```

**Technical wrinkle to solve first:** a Zod schema built with `z.object({...})` at module scope (outside any component) cannot call the `t()` hook, because hooks only work inside a component's render. The fix is a **schema factory function** that takes `t` as a parameter and is called inside the component body, memoized so it doesn't rebuild every render:

```ts
// module scope — no hook call here, just a function definition
const createLoginSchema = (t: ReturnType<typeof useTranslation<'auth'>>['t']) =>
  z.object({
    email: z.string().email(t('invalidEmail')).min(1, t('emailRequired')),
    password: z.string().min(6, t('passwordTooShort')),
  })

// the exported type is derived from the factory's return type, not from a
// module-scope schema instance — this still works at the type level because
// types are erased; `t` never has to be called to compute the type.
type LoginFormInputs = z.infer<ReturnType<typeof createLoginSchema>>

export const Login = () => {
  const { t } = useTranslation('auth')
  const loginSchema = useMemo(() => createLoginSchema(t), [t])
  const form = useForm<LoginFormInputs>({
    resolver: zodResolver(loginSchema),
    defaultValues: { email: '', password: '' },
  })
  // ...
}
```

Apply this `createXSchema(t)` + `useMemo` + `ReturnType<typeof createXSchema>` pattern to every file in the zod-schema list above.
