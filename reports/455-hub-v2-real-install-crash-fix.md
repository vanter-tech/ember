# Report 455

## 1. Identification
- **Report Number:** 455
- **Task ID:** EMBER-HUB-V2 bug fix (ad-hoc, post-plan) — "Ember Hub no pudo iniciar." on a real install
- **Predecessor Task:** EMBER-HUB-V2 Task 6 (report 454); this fix supersedes root-cause claims made during Task 4/5 verification (reports 452/453 — see §5)

## 2. Objective
User installed the real `EmberHubSetup-0.2.4.exe` produced in Task 5 and hit "Ember Hub no pudo iniciar." on every launch. Find the actual root cause via `systematic-debugging` (report 452's "Docker port conflict" theory, given without real evidence, turned out to be wrong) and fix it.

## 3. Modified Files
- Modify: `ember-hub/src-tauri/src/main.rs` (strip a `\\?\` verbatim-path prefix before writing paths into `hub.env`)
- Modify: `ember-hub/build-installer.ps1` (sort `backend/target`'s jar candidates by `LastWriteTime` instead of picking the alphabetically-first one)

No other source files changed. The third contributing issue (see §4.3) required no code change — only rebuilding `ember-hub/dist/runtime`, which isn't tracked in git.

## 4. What Changed? (three independent, stacked bugs)

**4.1 — Wrong jar selected (`build-installer.ps1`).** `backend/target/` had a leftover `ember-0.0.1-SNAPSHOT.jar` (ancient, pre-dates the Task 1/2 Swing-removal refactor) sitting alongside the current `ember-0.2.4-SNAPSHOT.jar`. `Build-AppImage`'s jar lookup was `Get-ChildItem -Filter "ember-*.jar" | Where-Object {...} | Select-Object -First 1` — unsorted, so it picked whichever `Get-ChildItem` enumerated first, which is alphabetical on this filesystem: `"0.0.1"` sorts before `"0.2.4"`. Every `-Stage appimage`/`-Stage installer` run — including this session's own Task 5 verification (report 453) — silently packaged the **ancient jar**, no matter how many times `mvn package` produced a fresh one. Fixed by adding `Sort-Object LastWriteTime -Descending` before `Select-Object -First 1`.

**4.2 — `\\?\`-prefixed paths break Java's `Path.of()` (`main.rs`).** Tauri's `app.path().resource_dir()` returns a canonicalized path, which on Windows carries a `\\?\` verbatim-prefix. `ensure_hub_env` baked that literal prefix into `hub.env`'s `EMBER_HUB_POSTGRES_BIN_DIR`/`MINIO_BIN_DIR`/`PUBLIC_KEY_FILE` values (confirmed directly: `Select-String` on the real generated `hub.env` showed `EMBER_HUB_POSTGRES_BIN_DIR=\\?\C:\Users\...`). `HubProperties.fromEnvironment` (shared by both the deleted Swing dashboard and the new headless orchestrator) parses every one of these with `java.nio.file.Path.of(...)`, which does not support the `\\?\` extended-path syntax at all and throws `InvalidPathException: Illegal character [?] in path at index 2`. This is a real bug independent of bug 4.1 — it would have broken the *new* code path too, on every fresh install, not just the stale-jar case. Fixed with a new `strip_verbatim_prefix` helper (2 unit tests, both passing) applied to `resource_dir` before deriving `app_dir`.

**4.3 — Stale jlink runtime missing `jdk.httpserver` (build artifact, not source).** Report 450 (Task 2) added `jdk.httpserver` to `ember-hub/jlink-modules.txt` (needed for `HubControlServer`'s `com.sun.net.httpserver.Filter`-based CORS filter, Task 1). But `ember-hub/dist/runtime` — the actual jlink-built JRE image bundled into every app-image — was **built before that change** and has never been rebuilt since (`Build-AppImage` only calls `Build-Runtime` `if (-not (Test-Path $runtimeDir))`, and the directory already existed). Confirmed directly: `java.exe --list-modules` on the shipped runtime listed `java.net.http` but no `jdk.httpserver`. Every launch threw `NoClassDefFoundError: com/sun/net/httpserver/Filter` from `EmberApplication.runHubSidecar` — invisible to the user because jpackage's non-console native launcher swallows the exception into a generic "Failed to launch JVM" message box instead of showing the real stack trace. Fixed by deleting/rebuilding `dist/runtime` (`-Stage all`); confirmed the rebuilt runtime now lists `jdk.httpserver`.

## 5. Why It Changed? (and why report 452/453 got the root cause wrong)
Report 452 attributed a crash-screen sighting during Task 4's own manual smoke test to "this dev machine's Docker Postgres/MinIO already hold 5432/9000" — a real fact (those ports were genuinely occupied at the time) but **an unverified guess presented as a conclusion**, not backed by reading the actual crash output. The real cause, even at that point, was almost certainly bug 4.3 (or 4.1, since the stale jar predates that test too) — the process crashed before ever reaching a Postgres port-bind attempt. Report 453 built and shipped the installer without ever actually launching the packaged result end-to-end (it only checked that `cargo tauri build` succeeded and that the NSIS script contained the firewall-rule string) — so the same latent bugs shipped straight through.

This time, `systematic-debugging` was followed properly: closing Docker (Phase 1 test of the original hypothesis) did **not** fix it ("Mismo error" from the user) — that falsified the guess immediately rather than accepting it. From there, direct evidence was gathered at each layer (raw `stderr` capture bypassing the Tauri shell → found the Swing-era stack trace → found the stale jar timestamp → found the jar-selection code path → fixed it → rebuilt → new failure → `--win-console` diagnostic build to unmask jpackage's generic dialog → found the real `NoClassDefFoundError` → traced it to the never-rebuilt runtime). Each fix was verified against real evidence before moving to the next hypothesis, per the skill's Iron Law.

## 7. Known follow-ups (not fixed here, flagged not silently dropped)
- `printing-agent/build-installer.ps1`'s `Build-AppImage` has the **exact same unsorted jar-selection pattern** (`Get-ChildItem -Filter "printing-agent-*.jar" | Select-Object -First 1`) — already flagged once in report 441 and never fixed. It hasn't bitten in practice yet only because `printing-agent/target/` hasn't accumulated multiple matching jars. Worth applying the same `Sort-Object LastWriteTime -Descending` fix there proactively rather than waiting for it to actually fail.
- `Build-AppImage`/`Build-Runtime`'s staleness check (`if (-not (Test-Path $runtimeDir))`) has no way to detect that `jlink-modules.txt` changed since the runtime was last built — it will happily keep reusing a stale runtime forever unless someone manually deletes `dist/runtime` (as happened here). A content/hash check against `jlink-modules.txt` would close this permanently; not implemented now to keep this fix minimal and scoped to the actual reported bug.
