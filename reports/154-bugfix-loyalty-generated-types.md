Swap the remaining hand-typed loyalty interfaces in `api.ts` for their now-regenerated `backend-types.ts` schemas (user re-ran `pnpm run openapi`), closing the "Still-owed" item noted at the end of the EMB-CLP backlog — same cleanup pattern as reports 128/134.

## What Changed?
- `LoyaltySettings`: hand-typed interface → `components['schemas']['LoyaltySettings']`; `LoyaltyAccrualMode` now derived as `NonNullable<LoyaltySettings['accrualMode']>` instead of a standalone union literal.
- `SettingsResponseWithLoyalty` (the `SettingsResponse & { loyalty?: LoyaltySettings }` intersection) removed entirely — the regenerated `SettingsPayload` schema already carries `loyalty?: components['schemas']['LoyaltySettings']`, so `SettingsResponse` alone is sufficient. `LoyaltySettings.tsx` dropped its `as Promise<SettingsResponseWithLoyalty>` cast on `getSettings()` and now types its mutation/save payload as plain `SettingsResponse`.
- `LoyaltyRewardResponse`/`CreateLoyaltyRewardRequest`/`UpdateLoyaltyRewardRequest`: hand-typed interfaces → their `components['schemas'][...]` equivalents. `LoyaltyTier` is now derived as `NonNullable<LoyaltyRewardResponse['requiredTier']>` instead of a standalone union literal.
- `RewardCatalogEntry`/`LoyaltyAccountResponse`: hand-typed interfaces → generated schemas. Note the schema name changed from `RewardCatalogEntry` to `RewardCatalogEntryResponse` server-side; kept the frontend alias name `RewardCatalogEntry` unchanged so no call sites needed renaming, just re-pointed the alias.
- Every generated loyalty schema field is optional (OpenAPI doesn't mark them required), unlike the old hand-typed interfaces. Fixed the resulting strict-null fallout at three call sites using the same `!` non-null-assertion pattern already established elsewhere in this file (e.g. `bill!.id!` in the same `Bill.tsx`): `reward!.id!` in `EditRewardModal.tsx`'s update mutation, `reward.requiredTier!` (×2, badge class + label) in `LoyaltySettings.tsx`'s reward table, and `loyaltyAccount.tier!` in `Bill.tsx`'s "you earned points" card. `loyaltyAccount.nextTier` needed no change — it's already guarded by a `&&` truthiness check in the same expression, which TS narrows correctly.

## Why It Changed?
Direct continuation of the "swap hand-typed interfaces for generated ones once regenerated" pattern (reports 128, 134). The regeneration was still owed from EMB-CLP-02/06/07/08 (reports 147/152/153), each of which added its loyalty type by hand because `backend-types.ts` hadn't caught up yet; the user ran `pnpm run openapi` this session to close that gap in one pass, as planned.
