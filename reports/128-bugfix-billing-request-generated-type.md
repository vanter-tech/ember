# Report 128 — bugfix-billing-request-generated-type

**Predecessor Task:** EMB-PAY-01..04 (Customer Payment Cycle, reports 124–127)

## Objective
Replace the one hand-typed request body left over from EMB-PAY-01 (`billingService.requestBilling`'s inline `{ splitMethod, participantCount }` object) with the generated `RequestBillingRequest` schema, now that the user has regenerated `backend-types.ts` against a live backend (`pnpm run openapi`).

## Modified Files
- `frontend/src/lib/api.ts`
- `frontend/src/lib/backend-types.ts` (regenerated by the user; committed as-is)

## What Changed?
- Added `export type RequestBillingRequest = components['schemas']['RequestBillingRequest']`, and `billingService.requestBilling` now builds an explicitly-typed `RequestBillingRequest` body instead of an untyped object literal.
- Added a short comment above `PendingDigitalPayment`/`WaiterBillState` clarifying they stay hand-typed on purpose: both model WebSocket broadcast payloads (`BILL_READY`/`SPLIT_PAID`/`DIGITAL_PAYMENT_INITIATED`), which never appear in the OpenAPI spec (it only documents REST responses) — no regeneration will ever produce a schema for them.

## Why It Changed?
At the time EMB-PAY-01 was implemented, `backend-types.ts` hadn't been regenerated since before that task's new `RequestBillingRequest` DTO existed, so the request body was left as a plain object literal. The user has since run `pnpm run openapi` against a live backend; this closes that gap now that the schema is available, and documents which of the other billing types are permanently exempt rather than leaving that ambiguous.
